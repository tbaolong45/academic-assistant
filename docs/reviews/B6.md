## Focus answers

1. **Filters and Do next — correct in code.** `WeekView` builds `ranked = f.forRanking.apply(store.items)` (`WeekView.swift:21`) and feeds only that to `doNext` (`:23`) and to `crunch` (`:31-33`). `BoardFilter.forRanking` resets group to `.all`, types/origins to empty and `showHidden` to false, keeping only `courses` and `hideUnsure` (`Model.swift:865`). Group/Type/Source/Show hidden therefore cannot change Do next or crunch; hidden items never reach either. The header picker counts and the board columns use the full filter, as specified. The only evidence is a unit check of the `forRanking` object, not of `doNext`/`crunch` output (finding 4).
2. **Restore — it clears the mark, with two edges.** `MarkActions` shows Restore when `deadline.mark != nil` and calls `act(nil, nil)` (`WeekBoardParts.swift:356`); `DeadlinePreview` accepts the optional state; `Store.mark` writes `nil` under every current `clusterKeys` key, saves and reapplies (`Store.swift:81-90`). A shown hidden card, a returned dismissed/snoozed card and the preview all get Restore. It is **not tested** (finding 3). Edge: only the *current* cluster's keys are cleared, so a mark on a member that has since left the cluster survives and can come back if that member rejoins; and P9 skipped the hidden item's AI title, so a restored card can keep its raw headline until the next `summarize()` (≤5 min).
3. **Prune only after a clean sync — the Moodle-warnings rule is implemented, but “clean” is too narrow.** `Store.swift:157` prunes only when `result.warnings.isEmpty` and the generation is current, **after** `downloadMaterials` and `scanDocuments`, so partial Moodle syncs and pre-scan pruning are fixed (F1f #1/#2) and PDF dates from this generation are live. But `result.warnings` covers **Moodle only**: an Outlook calendar fetch failure sets `outlookNote` and returns nil without a warning, and `calendarItems` is not persisted — after a launch, a failed first Outlook fetch leaves the board without Outlook items and the prune drops >30-day Outlook marks though the source still exists. PDF download/parse failures (`downloadNote`, `documentEvents` silently skipping a file) have the same shape. Finding 1.

## Findings

1. **Medium — the clean-sync gate ignores Outlook and PDF source failures.** `Store.swift:141-157`, `fetchOutlook` (`Store.swift` ~246-258), `downloadMaterials`. Scenario: the user has a done mark on an Outlook “Career Fair” event from 40 days ago; the app launches (calendarItems is in-memory only), the first sync's `OutlookCalendar.fetch` fails (offline/expired link); `sync` leaves `calendarItems` empty, Moodle has no warnings, `scanDocuments` runs, `pruneBoardMarks` drops the Outlook mark; a later good fetch brings the event back **unmarked**. Same for a PDF date whose download failed or whose parse `documentEvents` skipped (no warning is recorded). Fix: require success flags for Outlook (fetch attempted/succeeded or no link), mail and the PDF scan/download, or carry the previous live keys for those sources forward, before pruning.
2. **High (verification) — B6/F1f are not tested by the built binary.** The commit adds `filter:`, holiday, Monday-snooze and 30-day checks, but `SelfCheck.swift` is 01:00 and the release/app bundle are 00:57; the green run contains none of the B6 checks. `build-app.sh` has not been run after the commit, so the B6 done criterion is unverified. A rebuild is required before this can be called green.
3. **Low — Restore has no test and is incomplete across cluster changes.** No check exercises the Restore path (button, clearing, re-show). `Store.mark(nil)` clears only the current `clusterKeys`; a mark on a member that left the cluster stays in `board-state.json` and can resurrect if it rejoins. A restored card also skips the “hidden needs no title” P9 path until the next summarize. Add a pure test (mark → applyMarks hidden → mark(nil) → visible, marks empty) and decide whether stale member keys should be cleared eagerly.
4. **Low — the Do next/crunch filter invariant is only unit-tested as a value.** The test checks `picky.forRanking` fields, not that `doNext`/`crunch` output is identical when `group`, `types`, `origins` or `showHidden` change. Add a small integration check over a fixture list (same courses/hideUnsure, different other filters → same ids/order).
5. **Low — `isUnsure` and type/origin filters have edge semantics.** A course-page-only cluster with a classified kind is not unsure (only “all PDF”, “all unclassified” or a low confidence triggers), and the Type filter uses the cluster winner's `kind` only. Both match the words in §4 narrowly but deserve a comment/test if the architect meant “any text source” for unsure.
6. **Nits:** `BoardFilter` is stored in `@AppStorage` (UserDefaults), which is a view preference and contains only course ids/types/origins — no titles, fine; the filter’s course menu uses `Label(...).tint(hue)` which may tint the label text rather than a dot; `Clear filters` preserves the group, as intended.
