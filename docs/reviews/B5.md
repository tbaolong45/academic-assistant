## Focus answers

1. **board-state.json privacy — clean in the code.** `Mark` (`BoardState.swift:6-12`) has only `state`, `until`, `itemDate`, `at`; the dictionary keys are `BoardState.key(memberKey)` = SHA-256 (`:21`), and `BoardState.save` uses `writeOwnerOnly` (`:20`). No title, course name or text is stored; the folder/file are 0700/0600 (test). I found no place that writes a `Deadline`/title into the file. (The test checks permissions but not the file body; a tiny assertion that the encoded JSON does not contain a fixture title would make that explicit.)
2. **A mark on one member covers the cluster — yes.** `Deadline.clusterKeys` is the winner plus every `alsoIn` member (`:26`); `Store.mark` writes the mark under every one (`Store.swift:81-87`); `applyMarks` checks all keys and takes the latest mark (`:31-45`), and the B5 test proves a mark on a non-winner hides the merged item. `Store` also computes prune liveness from every cluster key, so a mark on an `alsoIn` member stays live.
3. **Dismiss comes back on a date change; done stays done — yes in the logic.** `applyMarks` (`:35-44`): `moved = |date − itemDate| > 12 h`; `.done` is always hidden; `.dismissed` is hidden only while not moved and sets `dateChanged` when moved; `.snoozed` is hidden until `until` unless moved, in which case it returns now and is tagged. The tests cover dismiss/done/snooze; there is no test for the moved-snooze branch or the 12 h boundary.
4. **Pruning can still drop a live mark on a partial sync — see finding 1.** The pure rule is right (`pruneMarks` keeps a mark while its key is in `live` or its `itemDate` is within 30 days), and `Store` feeds it `rawBoard` (unfiltered by marks) so hidden-but-live items are counted. But `pruneMarks` is called unconditionally after a *successful* sync, before the warning state is used, and before the PDF scan.

## Findings

1. **Medium — a partial sync can prune a live mark.** `Store.swift:141-147`: on a successful `MoodleSync` with `result.warnings` (a course's grades/contents call failed, a course part was skipped, submission status unavailable), `publish()` builds `rawBoard` without that course's items, and `pruneMarks` runs immediately with that incomplete `live` set. A done/dismissed/snoozed mark whose `itemDate` is more than 30 days past is dropped, though its item still exists in Moodle; the next good sync brings the item back **unmarked** (done becomes visible again). Fix: skip pruning when `result.warnings` is non-empty (the Store already tracks `lastSyncPartial`), or carry forward the previous sync's keys for the sources that failed.

2. **Low–Medium — pruning runs before the PDF scan.** `Store.swift:146` prunes, `:151` then calls `scanDocuments`; a mark on a PDF-only item is live only if `docs` already holds that PDF's dates. On a launch with no cache (or if the init scan was superseded by a Sync-now), `docs` is empty at prune time, so an old (>30 d) PDF mark can be dropped before the scan re-adds its item. Move the prune after `scanDocuments` (or after all sources have contributed).

3. **Low — `live` means “on the board”, not “in a source”.** `rawBoard` comes from `boardItems`, which drops events that Jev labels `info`/`grades`, bare-date lines and items deduped by `sameItem`. A marked item that later falls out of the board for one of those reasons is pruned after 30 days although the announcement/PDF still exists; if it comes back, it is unmarked. This is the literal “key no longer exists in any source” vs “no longer on the board” gap; use the source/subject keys for liveness or keep such marks.

4. **Low — the “Date changed” tag is thin.** `WeekBoardParts.swift:160` adds `Tag(text: "Date changed", edge: amber)` only on the week card: Do next chips and the preview do not show it, so a dismissed item that returns into Do next has no visible reason; and it is a status colour on an edge with no icon (U4's "label + icon" rule). Add the tag to the chip/preview and a small `arrow.triangle`/`exclamationmark` icon.

5. **Low — Done/Dismiss is one-way in this build.** There is no “Show hidden” view until B6, and `MarkActions` only exists on visible cards/chips/preview (`WeekBoardParts.swift:347-359`); a mistaken Done or Dismiss can only be undone by editing `board-state.json`. The design §3.4 deliberately leaves the unmark UI to B6, so this is expected between B5 and B6 — flag it if the build is used as a daily driver before B6.

6. **Low — snooze expiry is only recomputed when data or marks change.** `Store.applyBoardMarks` (`:90`) uses `now` once; the comment accepts up to a 5-minute delay at the next sync, and a failed sync’s `publish()` still refreshes it, so this is minor. A long offline stretch or a hung sync can keep a snoozed item hidden past `until`.

7. **Low — conflicting marks on joining members.** `applyMarks` takes the mark with the largest `at` among the cluster’s keys. Normal marking writes all current keys, so conflicts only arise when a new member joins with an older mark under its key; a newer dismiss on that member can then override a done mark on the original member. Priority order (done > dismissed > snoozed) or “the mark written last for this cluster” would make done-stays-done robust.

8. **Nits:** the 30-day prune boundary uses `itemDate > now − 30 d`, so exactly 30 days old is dropped though the design says “more than 30 days past”; “Monday 08:00” returns *today* 08:00 when it is Monday before 08:00 rather than next Monday (`snoozeOptions`, `:58`).
