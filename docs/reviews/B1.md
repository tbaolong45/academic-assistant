Scope: `Model.swift` (`BoardItem`, `boardItems`, `between`, `headlineCache`, the private `deadlines(in:)`), `Store.swift` (board in `subjects.didSet` and at the end of `init`), `WeekView.swift`, `HomeView.swift`, `App.swift`, `Moodle.swift` (date regexes as static lets), `SelfCheck.swift`.
Snapshot: `Model` 22:55 (its U1 edit at 23:16 did not move the B1 lines), `Store` 22:53, `WeekView` 22:54, `HomeView` 22:54, `App` 23:10, `Moodle` 22:54, `SelfCheck` 23:11. `SchoolMail.swift` changed at 23:12 (the R1 fix landing) and is unrelated.

Verdict: the slicing, the `deadlines(from:days:)` wrapper, the removed `weekItems`, and the static regexes are behaviour-preserving on everything I could check. One real semantic change remains — the edge the coordinator flagged — and it is not covered by the new tests.

## Findings

1. **Medium — the event-vs-assessment dedupe now spans all dates and can hide a current event.** `Model.swift:247-264` (`titles` at 260, filter at 264), reached from `boardItems` (`Model.swift:238-239`) with `.distantPast..<.distantFuture`.
   `titles` is built from every ungraded assessment and every open assignment at any date; an event is dropped if its title starts with one of those names. Scenario: a Moodle assignment "Reading response 3" is still open, due in three weeks (or is three weeks overdue and never submitted); the teacher posts "Reading response 3 workshop" for Thursday → `sameItem("reading response 3 workshop", "reading response 3")` is true → the Thursday event vanishes from the whole board, while the old `deadlines(from:days:)` only compared items inside that 7-day window and showed it. With a generic manual grade item ("Lab", "Quiz", "Assignment") this suppresses every event whose title starts with that word.
   Fix for a "behaviour-preserving" step: build `titles` per event from items dated near it (e.g. ±7 days), or keep the dedupe window-scoped until B4's cluster replaces it. If the change is accepted for one step, it needs a test (finding 3).

2. **Low — `board` is recomputed on every intermediate `subjects` assignment, not once per sync.** `Store.swift:8` (`didSet`).
   A single sync assigns `subjects` about eight times: `setLive` from `apply` and its `summarized` (`Store.swift:59`, `64`), `addOutlookCalendar` (`190`), `addSchoolMail` (`212`), `applyDocumentDates`' map and `summarized` (`121`, `126`), then the `classify` and `summarize` completions (`147`, `179`). Each run rebuilds `deadlines` over *all* dates, runs `mainPoint` per item and sorts, synchronously on the main actor. With a real semester of events/PDF dates that is roughly 8× the work B1 set out to do once, in eight main-thread chunks.
   Fix: recompute once at the end of the sync pipeline, or coalesce (aligned with T6 proposal 2, "one publish per sync"). `init` also computes twice when there is no cache (`Store.swift:10` default plus `45`) — trivial.

3. **Low — the acceptance test cannot catch the change in 1.** `SelfCheck.swift:33`, `36-39`.
   `SelfCheck.swift:33` compares `boardWeek` with `deadlines(from:days:)`, but both now call the same private `deadlines(in:)`; only the window differs, and `weekIDs` (`36-39`) are all assessment/assignment ids because `Subject.all` has no `events` arrays at all. So the event path — the dedupe and the event headline — is untested. Add a fixture subject with an event whose title prefixes a *distant* open assignment, assert the event still appears (the exact edge), and one assert that its `headlineCache` is the `mainPoint`.

4. **Low — sidebar badge reads the clock twice.** `App.swift:102` calls `weekStart(of: .now)` twice; if the clock crosses Monday 00:00 between them, the range mixes two weeks. Capture `let start = weekStart(of: .now)` once.

## Checked and clean
- `boardItems(...).between(now, now+7d)` reproduces the old week set and order on the sample (self-check: 9/9 ids); `WeekView`'s week slice uses calendar days (`WeekView.swift:16`) exactly as the old `weekItems` did.
- `HomeView.swift:15/19` and `App.swift:102` slice from `now`/`weekStart`, so they keep the old "from now" semantics; `crunch` still receives the visible week filtered by `date >= now && (toSubmit || exam)` (`WeekView.swift:29`); "Do next" still filters `.toSubmit` (`:20`), so D2 stays for B3.
- The `.distantFuture` trap: an assignment with no due date (`AssignmentItem.due == .distantFuture`, `Moodle.swift:410`) is *not* included, because `boardItems` passes a half-open `..<Date.distantFuture`; dateless assignments do not poison `titles`. Keep that bound when finding 1 is fixed.
- `deadlines(from:days:)` still window-scopes for its callers (`--moodle-check`, tests); `Deadline.headline` still falls back to computing when `headlineCache` is nil, so direct `deadlines()` users are unaffected.
- Static regexes: same patterns, hoisted; `NSRegularExpression` is immutable/thread-safe, and lazy static init is thread-safe, so the detached PDF parse is fine. `mentionedDates("Quiz on 3rd October")` check passes.
- `Store.init`'s manual `board` recompute is necessary (observers do not fire for `subjects` inside `init`) and runs after the cache/mail merge; correct.
