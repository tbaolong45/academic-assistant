## Focus answers

1. **Stale publishes after the generation gate.** No *source* publish can land after a transition: `sync()` checks `isCurrent` after the concurrent fetches (`Store.swift:114`), and there are no awaits between that check and `use`/`publish` (`:120-122`); `scanDocuments` re-checks after the detached PDF parse (`:146`); `publish` itself refuses unless `isConnected` and `lastSynced != nil` (`:82-85`), which is false in sample mode. The ungated publishers are the AI completions (`classify` `:169`, `summarize` `:200`) — they rebuild from the *current* `base`/`docs`/`mail`, so they cannot put old source data over newer data, but they are extra publishes and `summarize`'s **prune** uses the subjects current at completion (finding 1). `fetchOutlook`/`fetchMail` set their notes before the gate (`:214`, `:244`), so a note can appear after a disconnect (finding 5).
2. **Disconnect mid-sync.** The sample dashboard stays sample: `disconnect` bumps the generation, cancels `autoSync`/`syncTask`, sets `base`/`docs` empty and `isConnected` false (`:347-361`); the running sync's gate (`:114`) or scan gate (`:146`) drops its result, and `publish` refuses while `isConnected` is false or `lastSynced` is nil (`:82-85`). The remaining paths are AI tasks started before the disconnect (not cancelled, finding 1), late notes (`:214`, `:244`, download note `:138-139`), and files that `downloadMaterials` keeps writing after the disconnect. No real mail/Outlook item is merged into `subjects` while it is sample.
3. **`Summarizer.prune` on sample data.** **Fails in one path:** a `summarize` run that is in flight when the user presses Disconnect prunes and saves the paid titles against `Subject.all` (finding 1). The guard at `:177` checks `isConnected` only at the start, and the `Task` at `:185` is unstructured, so it is not cancelled. With sample data that has no events, `todo` is empty and the function returns before the prune, which is why a plain sample run looks safe — that is accidental, not a guard.
4. **Init PDF scan ordering.** Works for its purpose: `init` publishes the cache, then `startAutoSync(scanFirst: true)` runs `scanDocuments(generation 0)` **before** the first `sync()` bumps the generation (`:55-62`, `:87-96`), so cached PDF dates are on screen immediately and the first sync's own scan (`:126`) replaces them. Two problems: the scan is awaited, so the first sync waits for the whole PDF scan (latency), and with **no cache** the scan runs on `Subject.all` (finding 2). A `syncNow` during the scan bumps the generation and correctly drops it; the sync's later scan re-does it.

## Findings

1. **Medium — Disconnect during `summarize` prunes and persists paid titles against the sample subjects.** `Store.swift:176-204` (prune `:198`, save `:199`), `disconnect` `:347-361`, `Summarizer.prune` `Summarizer.swift:144-146`.
   Scenario: a summarize run is in the loop (Jev/DeepSeek calls); the user presses Disconnect; `subjects` becomes `Subject.all`; the loop finishes, `prune(titles, to: subjects)` computes an empty `live` set and returns `[:]`, `save` writes that to `summaries.json`, and `publish` is blocked only afterwards by `isConnected`. All paid titles are gone from memory and disk; reconnecting means paying again. The loop also keeps calling Jev/DeepSeek after the disconnect. Fix: keep the task handle and cancel it in `disconnect`, and/or capture the generation/subject snapshot at the start and prune against that, skipping prune/save/publish when the generation changed.

2. **Medium — with no cache, the init scan runs `classify()` on the sample data.** `Store.swift:55-62`, `:143-151`.
   `init` sets `isConnected = true` and calls `startAutoSync(scanFirst: true)` even when `MoodleCache.load()` returned nil; `scanDocuments(0)` then passes its gate and calls `classify()` (`:149`), which sees `hasJevKey` and sends `Subject.all`'s sample announcements to Jev (paid). `summarize()` (`:150`) currently returns early because the sample has no `events` (`todo` empty), so titles are not pruned today — but only by that accident. Fix: skip the init scan/AI unless `lastSynced != nil` (source live), and/or skip `scanFirst` when there is no cache.

3. **Low–Medium — the init scan serialises before the first sync.** `Store.swift:87-96`, `:143-151`.
   `await scanDocuments(gen)` delays the first `sync()` until every cached PDF has been parsed; with a full syllabus set this pushes fresh grades/mail back by the scan time (P2's latency claim is "slowest source", not "scan + sync"). The scan also spawns `classify`/`summarize` tasks that run while the sync fetches, adding publishes and paid work on cache events that the sync may replace (their titles are pruned later, correctly, but the calls were paid). Correctness is fine; the ordering is a latency/cost choice worth measuring.

4. **Low — AI publishes are not generation-gated, and `summarize` prunes against whatever `subjects` is current.** `Store.swift:169`, `:200`. After a newer sync has started but not published, a finishing `classify` rebuilds from the old `base` (same data as shown) — harmless; after a disconnect it is stopped by `publish`'s guard. The important consequence is finding 1. Pass the generation (or a subject snapshot) into the AI tasks and check it before prune/publish.

5. **Low — disconnect leaves per-session UI state and late notes.** `disconnect` does not clear `mail`, `calendarItems`, `mailNote`, `outlookNote`, `downloadNote`, `syncing` or `downloading` (`:347-361`). A fetch that was in flight can still set `mailNote`/`outlookNote` (`:214`, `:244`) or the download note (`:138-139`) after the sample data is shown, and if the cancelled sync unwinds slowly the UI keeps "syncing"/"downloading" and `Sync now` stays disabled. `publish` blocks the data itself (focus 2), so this is cosmetic. Fix: clear the notes and flags in `disconnect` (and decide whether `mail`/`calendarItems` — separate Gmail/Outlook accounts — should survive a Moodle disconnect; today they do, so a reconnect to a different live session normalises the old mail/calendar items in until their fetches refresh).

6. **Test gaps.** `SelfCheck` covers `normalize` = old chain, the prune on `normalize`'s output (Outlook/mail titles), and `isCurrent`; nothing exercises disconnect-during-`summarize` (the sample prune), the no-cache init scan, or notes after disconnect. The two manual checks (one publish per sync, Disconnect mid-sync) are for the builder.
