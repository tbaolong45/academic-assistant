## Findings

1. **Medium — item 15's "nothing may loop forever while a course page is open" is not met.** `CourseView.swift:461-469` is static now (the 60 fps `TimelineView` is gone), but the course page embeds `ScoreChart` (`CourseView.swift:33`), and its `intro()` starts `.repeatForever` for the dashed "ants" (`ScoreChart.swift:74-78`, triggered by `.task(id:)` at `:50`). The same pattern remains in `AssessmentSheet.swift:68` (a 12 s endless spin when an ungraded assessment sheet is open, i.e. presented from the course page) and `WeekBoardParts.swift:349` (repeating glow on the deadlines board). Scenario: open a course → Scores tab, leave it open; a 60 fps dash animation keeps redrawing, so item 15's "re-measure idle CPU with a course page open, target under 5 %" has not been demonstrated and the stated condition is false on that tab (all respect Reduce Motion, and the files are outside F1's list — U5/U4 own them). Fix: drop `ants`' `repeatForever` to a one-shot or remove the dash animation in U5, then take the course-page CPU measurement.

2. **Low — item 9 still has one silent cache-write path.** `Store.swift:212` saves every fetched mail with `save: { try? MailCache.save($0) }`. This swallows both `writeOwnerOnly` failures (a write error, or the chmod error thrown after the write) during the per-message saves. The final `save { try MailCache.save(mail) }` at `:219` surfaces a persistent failure, but if the write fails (e.g. disk full) and the app quits before that line, the per-message progress is lost and no `cacheNote` was ever set — the opposite of item 9's "surface the chmod failure as a store note". Fix: collect the first error in the closure and set `cacheNote` after the loop (or call the `save {}` helper there once the closure can reach the main actor).

3. **Low — item 12's predicate drops course-page dates on a partial sync.** `Store.swift:65` now carries only `isPDFDate` events into the new sync; if `core_course_get_contents` fails for a course (a `soft` warning, so that course contributes no `materials.text`), the new `s.subjects` has no course-page events while the old ones are no longer carried — that course's page dates disappear until a later successful sync (if the failure persists, indefinitely). Before F1 they were carried but then stripped by `applyDocumentDates`, so this is not a regression in the steady state; it is the remaining loss path of the fix. A warning is shown and notifications are suppressed for that sync. Fix later with B2's Origin/merge, or carry page events for courses that had a materials warning.

4. **Nit — item 3's re-entry error is reported as a Gmail refusal.** `SchoolMail.swift:326`/`:345` throw `MailError.server("busy")`, shown as "Gmail refused a request (busy)". It is not reachable from the current sequential callers; a dedicated `.busy` (or `.closed`) would be clearer. No security impact.

5. **Low/nit — item 7 does not protect two-digit-year dotted dates.** `Classifier.swift:150-155` protects `dd.mm.yyyy` / `d.m.yyyy` (year `19xx`/`20xx`) only. A `23.10.26 10.00` is 10 digits joined by dots/space, so the phone pass still turns it into `[phone]`. The spec names 4-digit-year forms, so this is an uncovered edge, not a spec violation; adding `\d{2}` years (or excluding dot-groups that form a plausible date) would close it.

6. **Nit — the per-byte reader check prints "(failed at 0)" when it passes.** `SelfCheck.swift:453`/`:463`: `splitAt` stays 0 on success, so the green line reads like a failure in the log. Cosmetic.

7. **Test gaps (not blockers).** No self-check for item 2/3 (the spec allows skipping if they cannot be tested without the network — the test writer should say so explicitly), none for item 9's write-then-throw, and item 5's text is only covered indirectly by the `badCredential` guard test. Item 4 stays a manual `--mail-check`.
