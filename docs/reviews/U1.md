## Verdict
The tokens, course ramps, marks and washes match the approved Campus tables exactly, and the numeric checks pass when computed independently. No blocker. Two low observations below: the sample course still uses legacy blue, and I could not run the palette self-checks (the binary predates them).

## Findings

1. **Low — the sample dashboard still shows a blue course.** `Model.swift:286` (`hue: .blue` for Linear Algebra). `Hue.courseHues` is now `[.green, .orange, .yellow, .magenta, .violet]`, so synced courses are fine and cached `.blue` subjects are recoloured on the next sync, but the app's sample/demo data (what the user sees before connecting) still puts legacy blue next to the new blue UI — the exact clash D4 removes. The `Theme.swift` and `Model.swift` comments say this is deliberate ("old caches, sample data"), so this may be accepted; if not, switch the sample's first course to `.green` (the first `courseHues` entry) so the demo shows the new assignment order.

2. **Low (verification, not code) — the U1 palette checks were not in the binary I could run.** `SelfCheck.swift` is 23:18; `.build/release/AcademicAssistant` is 23:17, and a `--self-check` run shows no `palette:` lines. So I did not run them. I did compute the same numbers independently from the `Palette` hexes and they pass:
   - every §4 text pair ≥ 4.5 in both appearances; worst light `text3`/`raised` **4.810**, worst dark `onAccent`/`accent` **4.651** — matching the design's stated 4.81 / 4.65;
   - each course ramp is monotone (light decreasing, dark increasing) and band 0 is ≥ 2:1 on `surface` (light 2.06–2.23, dark 2.07–2.29);
   - `text` and `text3` stay ≥ 4.5 on every card wash (worst 4.67 light orange, 4.68 dark yellow, as the design says);
   - `courseHues == [.green, .orange, .yellow, .magenta, .violet]`, no blue, no repeats.
   Re-run `./macos/build-app.sh` after the 23:18 edit so the checks the test writer added are actually exercised.

3. **Nit — `Tech.neon` now resolves to `accentInk`, and some existing views still use it as a fill** (progress bars, glows, button backgrounds) until U2–U4 move fills to `accent`/`accentSoft`. That is what the U1 row prescribes, and the app is still forced dark (`App.swift:38`) so the step looks blue; just noting the fills are the darker ink blue for now.

## Checked and correct
- `Palette` matches §4 token-for-token: `bg` f4f6fa/0f141c, `surface` ffffff/171d27, `raised` eef2f8/1f2733, `line` d9e0ea/2b3442, `text` 0f172a/e8edf5, `text2` 475569/a9b4c4, `text3` 5f6b7d/8d99ab, `accent` 2563eb/2f6fe4, `onAccent` ffffff/ffffff, `accentInk` 1d4fc4/7eaaff, `accentSoft` e6eefd/1a2a47. Status tokens (`good` 0ca30c, `warning` fab219, `critical` d03b3b) are from the dataviz reference set and are documented "always with an icon and a label".
- Every `Hue` ramp (green, orange, yellow, magenta, violet, slate) matches §3 in both appearances, as do the categorical marks and the wash table (including 5e6a7b/939fb0 for slate and f7f3fd/26253d for violet). The legacy `.blue` entry keeps a full ramp so old caches still decode, and it is not in `courseHues`.
- `Hue.palette` switches over all seven cases (no `default`), so a future case is a compile error; `Hue.courseHues` is fixed order and never cycled.
- `Token` is a `Sendable` value of two hex strings; `color` is an `NSColor` dynamic provider keyed to `aqua`/`darkAqua`, so one token serves both appearances. `Color(hex:)` is sRGB and only used with six-digit values.
- `Tech` is the thin alias the U1 row asks for: `bg`/`panel`/`panelHi`/`line`/`text`/`text2`/`text3` map to the matching palette tokens and `neon` to `accentInk` (the 4.5:1 ink, for text and icons). The build at 23:17 compiles with it.
- The new checks in `SelfCheck.swift` cover the reference contrast (white/`#2563eb` 5.17), every text pair per appearance, the five ramps, `courseHues`, and an old cache with `"hue":"blue"` decoding to `.blue` — matching the test-writer list in §6.
