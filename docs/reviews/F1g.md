## Focus answers

1. **Can a non-anchor bridge still form? No, not through a third member.** `loose[root]` holds every non-anchor index in the cluster; before a union, every loose member of one root must be `close()` to every loose member of the other (`Model.swift:604`, `:640-648`), and `same` itself requires `close` for two non-anchors (`:635`). The union guard therefore enforces the invariant for every pair, including a bridge through an anchor (an anchor's loose set is empty, but the two non-anchor sides are still checked). A bridge is only possible through the intended allowances: same local day / ≤12 h, a ≤7-day title range, or an explicit move supersede. The new `Seminar` activity+two calendar test exercises this. Caveat: the “range” allowance is broader than the spec (finding 3).
2. **`moveCue` still has real false positives and negatives.** The `(?=\d|…)` lookahead treats **any digit** as a date. `"The quiz on 20 Oct has moved to room 3"` matches `moved … to 3`; `mentionedDates` then drops every date before `cueEnd`, so the 20 Oct event is **lost entirely** (finding 1). It also misses base/‑ing/third-person forms for five verbs: `extending`, `extends`, `changing`, `changes`, `delaying`, `delays`, `shifting`, `shifts`, `pushing`, `pushes` (finding 2). Positives (base/past forms, date words, “to next Monday”, “to the 1st of November”) and the negative cases in the test pass.
3. **Range ≤7 days: the size limit is right, the “range” detection is too broad.** `onDays` takes **any** title with two or more month/day pairs whose span is ≤7 days as a range of days (`Model.swift:607-618`), so `"1 Dec, 5 Dec"` (two separate dates) makes both days count as the item's own day and can close/merge a different item on the second day. Conversely `"Dec 1-2"` is not recognised as a range (only `"1-2 Dec"` is), which is a safe duplicate. The tests cover `1-2 Dec` and `1-9 Dec`, not the two-separate-dates case.
4. **All-sources prune gate: mostly fixed, one blind spot.** `Store.swift:161` requires no Moodle warnings, an Outlook result when a link exists, a mail result when an account exists, no download failures and a current-generation scan — so Outlook/mail/download failures no longer prune. But `scanDocuments` returns a simple Bool; a PDF that `PDFDocument` can't read (or a file skipped as >300 MB) leaves `docs` short while the scan still reports success, so marks on those PDF-only dates can still be pruned (finding 5).

## Findings

1. **High (conditional) — a false move cue can delete a real date.** `Moodle.swift:540` (lookahead `\d`) + `:600-626` (only dates at/after `cueEnd` are kept). Scenario: “The quiz on 20 Oct has moved to room 3.” The cue is `moved … to 3`; `cueEnd` is after “3”, the only date is before it, and the message produces **no event**. Same for “moved to 3rd floor”, “changed to 10:00”, “moved to 204”. This is exactly the vanished-card class F1g is meant to prevent. Fix: make the lookahead date-like (`\d{1,2}(st|nd|rd|th)?\s+(of\s+)?month`, `month\s+\d`, weekday/today/tomorrow), not any digit; and/or discard pre-cue dates only when at least one date after the cue exists.
2. **Medium — `moveCue` does not accept all base/‑ing forms the comment claims.** `Moodle.swift:540`: `push(?:ed)?`, `extend(?:ed)?`, `delay(?:ed)?`, `shift(?:ed)?`, `chang(?:e|ed)` accept base/past but not `pushing`, `extending`, `extends`, `delaying`, `delays`, `shifting`, `changes`, `changing`. “We are extending the deadline to 4 Nov” is not a move; no supersede, no mark. The test list only exercises base/past forms, so this is untested.
3. **Medium — any two dates in a title are treated as a range.** `Model.swift:607-618`. A title such as “Quiz 1 on 1 Dec, Quiz 2 on 5 Dec” yields `onDays = {Dec 1, Dec 5}` (span 4 ≤7), so a different “Quiz” item on Dec 5 can be `close` and merge on the strength of a range that isn't one. The rule should require a range token (`1-2 Dec`, `1–2 December`) rather than “two dates within 7 days”. No test for the separate-dates case; `onDays` also unions the item's own date even when it is outside the named range (edge).
4. **Low/Medium — P9 #3 still pays for an event deduped behind an assessment.** `Summarizer.targets` now filters `hasContent` (`Summarizer.swift:157`), but not the `sameItem` event-vs-assessment dedupe that `deadlines()` applies. A “Quiz 3 closes” announcement within ±7 days of the “Quiz 3” assessment is dropped from the board but still gets a Jev/DeepSeek title, contrary to F1g #3 (“not deduped behind an assessment”). The new test only covers the bare-date (`hasContent == false`) case. Add a board-membership check (event id present as a winner or `alsoIn` member) or mirror the dedupe.
5. **Low — the scan half of the gate has no per-file failure signal.** `Store.swift:161` trusts `scanned`; `MaterialStore.documentEvents` silently skips PDFs whose text is unavailable, and `wanted` skips files >300 MB. A mark on a PDF date can still be pruned although the file exists but couldn't be parsed/downloaded that run. Return a per-file/scan warning (or skip the prune when any configured PDF is unreadable) to finish B6 #1.
6. **Low — Restore clears marks by value, not by ownership.** `Store.swift:85` removes **every** mark whose value equals `d.mark`; two clusters marked with identical `state/until/itemDate/at` would lose both, and a left member whose mark value changed since the split would survive. The value match is a reasonable way to catch left members, but a test for the split/rejoin case is missing (F1g test list).
7. **Low — “Dec 1-2” ranges are not detected.** `namedDays` adds the first day only for `<digits>-<digits> <month>`; `"Dec 1-2"` gives just `Dec 1`, so the two mentions stay two cards. Duplicate rather than vanished, so acceptable; add it to the range regex if the architect wants symmetry.
8. **Verification — the 01:26 binary predates the 01:27 commit and the 01:28 SelfCheck.** Some new F1g checks (calendar/activity bridge, `1-9 Dec`, P9 bare event, the B6 #1 no-prune test) are not in the run above. Rebuild before calling the step green.

## Checked and correct
- **Anchor/non-anchor rule:** `anchor = via ∈ {.moodleActivity, .syllabus}`; anchor pairs keep the 3-day window; two non-anchors use `close` (same local calendar day, ≤12 h, ≤7-day title range, or a stated move within 30 days) (`Model.swift:598-635`). `loose` enforces the pairwise invariant at every union (`:640-648`); the activity+calendar bridge test stays two clusters.
- **Existing nets kept:** number-set union guard, same-ref/different-date guard, calendar/Outlook different-ref pair guard (with the new comment about pre-B2 nil refs), weekday day-set guard, `movedAfter` posted-order rule.
- **Range:** `onDays` uses the item's own **title** only (`namedDays`), year-nearest mapping and a ≤7-day span; `1-2 Dec` counts both days, `1-9 Dec` does not; the course-page + PDF “National Day” pair merges, “Commemoration Day” stays separate.
- **Move cue positives:** the six `cueYes` cases pass, `"moved from 20 Oct to 1 Nov"` keeps only 1 Nov, and “reschedule … to Friday, 9 October” keeps 9 Oct with `moved = true`; the four `cueNo` cases pass.
- **P9:** `hasContent` is applied, the hidden set now covers `.syllabus` anchors as well as `.moodleActivity`, and the bare “Dec 8 — -” event gets no request (in the 01:28 test; rebuild to run it).
- **Prune gate:** Moodle warnings + Outlook (`!hasOutlookLink || items != nil`) + mail (`!hasMail || fetched != nil`) + `downloaded` + `scanned` + generation (`Store.swift:161`); the Outlook/mail/download paths that motivated B6 #1 are covered. Outlook/mail fetch failures no longer prune; only the scan's per-file blind spot remains.
- **Restore:** clearing by the old mark value catches keys of members that left the cluster (Store.swift:81-87), improving “fully undo”; see finding 6 for the edge.
- **Build:** the 01:26 binary (pre-commit) passes all checks it contains; the source commit is 01:27 and `SelfCheck` 01:28, so a rebuild is needed for the full set.
