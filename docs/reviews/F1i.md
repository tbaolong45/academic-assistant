## Focus answers

1. **Can a changed Moodle file still be missed? Yes, in the cases the `>=` rule does not catch.**
   - A same-size update whose new `timemodified` is **newer** than the local mtime is fetched: after a download the local mtime is set to Moodle's time (`Materials.swift:66-68`), `isSaved` requires `local.modified >= file.modified` (`:23-26`), so a later server update fails the check.
   - Still missed: `file.modified <= 0` **disables the date check entirely** (`:26`), so a same-size replacement with no/zero `timemodified` is accepted; a **backdated** replacement (new `timemodified` older than or equal to the local mtime, including same-second and server-clock-behind cases); `file.size == 0` with `modified == 0` (any local file is accepted); and a content change that preserves size and `timemodified`. The approved `>=` deviation itself handles pre-F1i download timestamps, but the zero/backdated/same-second cases are real gaps. A >300 MB file is never downloaded by design; a locally edited copy is the documented blind spot.
2. **Cancellation rethrow — implemented and correct in the paths that matter.** `soft` calls `Task.checkCancellation()` before each call and rethrows cancellation before turning it into a warning (`Moodle.swift:96-100`); the submission-status closure does the same (`:178-184`). `courseData` calls `soft` for grades, contents and each forum, so a cancelled course stops at the next call; the group cancellation then unwinds. The only residual is that a `soft` call that **succeeds after** cancellation returns its value and only the following call notices; with no following call the course data returns, but the throwing group discards it. No test exercises `soft`/the status path directly (they are private), so this is code review only.
3. **Parse lock — no deadlock, but real starvation/head-of-line blocking.** `PDFCache.entry` takes the single global `parsing` Mutex for every parse (`Materials.swift:151-165`), calls `load()` and `Moodle.mentionedDates` under it, and nests the short `entries` lock inside. Lock order is always `parsing → entries`; `hit()` outside the parse lock only takes `entries`, and none of the current `load` closures re-enters `entry`, so I found **no deadlock**. However:
   - every PDF (different keys included) is serialized, contrary to the spec's per-key single-flight; a large `documentEvents` scan on the detached task holds the lock per file, and a preview's `mentions` call on the main thread can wait behind it, freezing the UI (potential starvation; `Mutex` fairness is not guaranteed);
   - a `load()` returning nil stores no negative entry, so two first-time callers of an **unreadable** PDF both call `load()` (the second after the first releases), so single-flight only holds for readable PDFs;
   - a `load` closure that itself called `entry` would self-deadlock on the non-recursive `Mutex`; current callers don't, but it is an easy future trap.
4. **PR review acceptance:** the `>=` deviation is intentional and only documented for pre-F1i download times and local edits; the zero/backdated cases above are not covered by that note.

## Findings

1. **Medium — a same-size change with no/zero `timemodified` is still missed.** `Materials.swift:23-26`: `(file.modified <= 0 || local.modified >= file.modified)` skips the date test when Moodle reports 0; a changed file of the same size is then “saved”. The same applies to `size == 0` plus `modified == 0` (any local file), a backdated replacement, and a change that preserves both size and timestamp. Fix: when `timemodified` is 0, compare the local mtime against a stored download stamp (or force a re-download on the first sync after an unknown timestamp), and document the backdated limitation.
2. **Medium — the parse lock is global, not per key.** `Materials.swift:151-165`. A full PDF scan serializes every parse; a `mentions` call from the main thread can block behind unrelated large PDFs, and with an unfair mutex a continuous scan can starve it. The spec asked for per-key single-flight; the comment admits “one lock for every parse”. Use a per-key in-flight map (or a small keyed lock pool) so only the second caller of the *same* PDF waits.
3. **Low — unreadable PDFs are not single-flight.** If `load()` returns nil, `entry` returns without storing a negative, so a second first-time caller enters the lock and calls `load()` again. This is not a deadlock, but it defeats the “parse once” intent for scanned/encrypted PDFs. Store a short-lived negative entry or an in-flight failure.
4. **Low — a cache hit ignores the current `posted` argument.** `PDFCache.entry(key, posted: when)` returns the stored `found` entries on a hit; if the local key is unchanged but Moodle's `timemodified` differs (the miss in finding 1), the cached relative-date years stay from the first parse. Pass/compare `posted` in the cache key or invalidate on a changed `posted`.
5. **Low — cancellation is only checked at the start of each `soft` and after an error.** A successful call that finishes after its task was cancelled returns; the next call checks. This is acceptable because the group discards the result, but a course whose last `soft` is followed by no forum call can return after cancellation. Add an explicit `try Task.checkCancellation()` after each call if the intent is immediate stop.
6. **Low — F1i verification is missing from the build.** The two F1i test blocks (`isSaved`/empty file, single-flight) exist in the working-tree `SelfCheck.swift` but are absent from the 01:50 binary, and the commit `652eed0` contains **no `SelfCheck.swift` change**. The `soft` cancellation test, the warnings-order/calls-counter test (F1i test-writer #3/#7) and a `PDFCache` local-key test are not present at all. Rebuild and commit the tests before calling F1i green.
7. **Low / accepted** — a >300 MB changed file is intentionally never downloaded; a locally edited copy is the approved blind spot; a pre-F1i file whose server update has a timestamp **earlier than its download time** (clock skew/backdate) is missed by the `>=` rule.

The old manual-key B7 test still passes.
- **Single-flight:** the second caller of a readable key waits on `parsing`, re-checks `hit()` and returns the first entry (`Materials.swift:155-165`); the working-tree test expects one load. Different-key parses queue (finding 2).
