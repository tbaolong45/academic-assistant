## Findings, most severe first

1. **High — the 30 s timeout and Task cancellation cannot interrupt a pending `send`; the session can hang forever.** `SchoolMail.swift:333-339` (`send`), `352-360` (`deadline`), consequence at `Store.swift:203-209`.
   `receive` has `withTaskCancellationHandler { … } onCancel: { connection.cancel() }` (`:341-350`), but `send` is a bare `withCheckedThrowingContinuation` around `NWConnection.send`. Scenario: the connection drops into `.waiting` (Wi-Fi gone, lid closed, stalled TLS write) after a command's line is handed to `send` but before its `.contentProcessed` completion fires. The 30 s timer throws `.timeout`; `defer group.cancelAll()` cancels the work task, but `withCheckedThrowingContinuation` ignores cancellation and nothing calls `connection.cancel()` (only `receive`'s handler does). `withThrowingTaskGroup` waits for all its children before returning, so `deadline` never returns — `session` → `addSchoolMail` never returns; `Store.syncing` stays true, so no further syncs and no `mailNote`/`syncError` is ever set. The same hole makes `close()` (`:321-324`) depend on a `send` completing on an already-failed connection.
   This directly breaks the spec rule "a per-command timeout (30 s) and Task cancellation close the connection".
   Fix: wrap `send` in `withTaskCancellationHandler { … } onCancel: { connection.cancel() }` (so cancellation fails the pending send), and/or cancel the connection in `deadline`'s timeout child (`connection.cancel()`) before throwing. A hard cancel in `session`'s catch is a cheap second net.

2. **Low–Medium (test gap vs the spec) — check (f) is not implemented as written.** `SelfCheck.swift:443-450`.
   The spec asks for the same reply fed in chunks **at every byte offset**, so the literal spans chunk boundaries. The test splits once at `whole.count - 12`; that boundary is inside the tagged line, while the literal is entirely in the first feed. The reader's literal-skip/`afterLiteral` path (`SchoolMail.swift:243-263`) — the part most likely to break — is therefore untested. Also, `:455` asserts `.badLogin` but not that its description contains neither fixture address nor password, and `:458-461` asserts the base64 line but not the "password isn't plain text" clause; `:437-440` cuts a `String` prefix (characters) rather than a byte literal, and the fixture is ASCII-only, so a mid-UTF-8 cut isn't exercised.
   Fix: loop `for cut in 1..<whole.count` on a small literal reply, expecting `nil` until the tagged line arrives and the identical literal at the end; assert the `MailError` description doesn't contain the fixture credentials; keep a multibyte fixture for the cut.
   The tests do pass on the 23:26 build (all seven P1 checks green).

3. **Low — `isSafeCredential` guards the AUTHENTICATE fields only in `session`, not structurally in `open`/`authenticateLine`.** `SchoolMail.swift:18`, `37-39`, `274-284`.
   `session` checks address **and** password before it creates the connection (correct, and before any TCP/TLS), so today's only production paths (`Store.addSchoolMail`, `Store.setMail`, `runMailCheck`) are guarded. But `IMAPConnection.open` accepts address/password and builds the SASL line without re-checking, and `authenticateLine` is a pure helper that will happily emit a line for input containing NUL. Nothing bypasses `session` today, so this is defence-in-depth rather than a live hole — but the point of P1 was to make "never marks read / never leaks" structural. Put the guard in `open` (or make `authenticateLine` throw/fail for unsafe input).

4. **Low — the connection type does not enforce one command at a time.** `SchoolMail.swift:268-319`.
   `count` and `reader` are actor state, and each `command` awaits inside `deadline`; actor reentrancy lets a second command interleave while the first is suspended, and the single `reader` then mixes replies (tags still increment, so responses can be attributed to the wrong command). Today the closure body is strictly sequential (`Store.swift:203-209`, `runMailCheck`), so it is not reachable. P4 adds progress and B7 parallelism, so this is worth an `isBusy` guard or an explicit serial queue now.

5. **Low — `runMailCheck`'s "newly seen" can false-positive on an expunged UID.** `SchoolMail.swift:374-380`.
   `newlySeen = unreadBefore ∩ targets − unreadAfter(targets)`. If a target UID disappears (expunged, or the server omits it) between the two FLAGS fetches, it is absent from the second set and counted as "newly seen", making the P1 proof fail spuriously on an otherwise correct client. Only the manual check is affected. Fix: compare against UIDs the second fetch actually returned (`present`), or re-query.

6. **Nit — `MailError.badCredential` wording.** `SchoolMail.swift:224`. The guard now exists to stop NUL field injection (and rejects empty strings); the message still talks only about "a line break or other control character". Say what it means: "The address or app password is empty or contains a control character (including NUL)".

## Checked and correct (the six-point list)
- **TLS**: `NWConnection(host: NWEndpoint.Host(host), port: 993, using: .tls)` (`:272`); no `NWProtocolTLS`/`sec_protocol_options`/verify block anywhere, so the system's default trust and hostname checks apply. Port 993 implicit TLS; `Network` imported at `:2`.
- **AUTHENTICATE PLAIN**: `authenticateLine` (`:37-39`) is `A<n> AUTHENTICATE PLAIN ` + base64 of `\0address\0password`; no IMAP quoting, no CRLF (guard rejects control chars, base64 has none), and the line is only handed to `connection.send` — no `print`, `Logger`, `NSLog` or error string ever contains it. `status(..., login: true)` maps any failure to `.badLogin` (`:46-57`), discarding the server's `[AUTHENTICATIONFAILED]` text; `MailError` descriptions are static (`:220-231`). `runMailCheck` prints counts only; its failure line is `error.localizedDescription`, which is a static `MailError` or an `NWError` description (no address/password). `isSafeCredential` covers both fields before the connection is created (`:18`).
- **EXAMINE**: sent once per connection (`:285`), after login and before any search/fetch; no `SELECT`, `STORE`, `\Seen` or mailbox-modifying command exists in the file (grep for `SELECT`/`STORE`/`BODY[]` finds only the doc comment). `UID FETCH … FLAGS` (`:314`) is a plain read under EXAMINE.
- **BODY.PEEK only**: `fetchCommand` (`:43`) is the only body fetch and uses `BODY.PEEK[]<0.262144>`; `message` uses it (`:308`); `runMailCheck` re-fetches cached mails through the same method.
- **Literal byte counting**: `command` returns `Data` (`:288-297`); `literal` (`:61-69`) works on bytes and takes exactly `{n}` bytes after `}\r\n`; the reader skips literals by byte count (`:250-256`) so a CRLF inside a mail body can't end a response early; `parse` receives `String(decoding:)` only after extraction. The 256 KB partial fetch is handled (short literal → shorter `Data`).
- **Timeouts and cleanup**: each command (including greeting and AUTHENTICATE) runs under `deadline` with a 30 s `Task.sleep` (`:353-360`); `receive` cancels the connection on task cancellation (`:341-350`); `session` closes on success and on error (`:20-28`); `close` best-effort `LOGOUT` then `connection.cancel()` (`:321-324`). The one gap is `send` (finding 1).
- **One connection per sync / one login**: `Store.addSchoolMail` does one `SchoolMail.session` and runs `search` + all `message` fetches inside it (`Store.swift:203-209`); `setMail` validates with its own short session (`:221`). `runMailCheck` also uses one session.
- **`--mail-check` wiring**: `App.swift:25` runs `runMailCheck()` (a `Never` function) before the `--login-check` branch and before any view/store use. It prints only `searched N · unread N · fetched N (parsed N) · newly seen N · re-fetched N cached, identical N` or `mail check failed: <localizedDescription>`; no address, subject, body or credential is printed.
