## Focus answers

1. **Can a fast sync lose an item? Yes — the merge is not a carry-over for several categories.** `Moodle.merge(fast:previous:)` (`Moodle.swift:109-126`) keeps previous assessments and materials, and carries previous course-page events and previous `.moodle` forum announcements. It does **not** carry previous **assignments**, `.message`/`.notification` announcements, or `.moodleCalendar`/action events. Therefore:
   - if `mod_assign_get_assignments` returns nil (soft warning), the fast sync has no assignments and every previous assignment disappears from the board until the next slow sync; the marks remain, but the cards do not;
   - even a fully successful fast sync drops previous messages/notifications that are not in the current 50-conversation/notification window, because the carry filter is `source == .moodle`;
   - a failed calendar/action call drops previous teacher/calendar events (only `.coursePage` is carried);
   - the General special-case carries only `.coursePage` pages, so an old General made of messages/notifications/calendar disappears even though a slow sync had it.
2. **Can a fast sync prune marks? No.** The fast branch returns before `downloadMaterials`, `scanDocuments` and `pruneBoardMarks` (`Store.swift:179-183`); `pruneBoardMarks` is only called on the slow path after a complete scan (`:190`). Marks survive a fast sync. The cost of the item loss is that a marked item's card is absent from `rawBoard` (the mark is not applied to anything); it reappears when the slow sync restores the item. Fast `summarize()` does prune **titles** against the lossy subjects, so paid titles for dropped messages can be thrown away and re-bought after the slow sync.
3. **Window-forward 5-minute throttle — present but measured from the wrong point.** `cameForward()` (`Store.swift:144-147`) requires `now − lastSlow > 5 min`; `lastSlow` is set to `started`, the **start** of the slow sync (`:184`), not its completion. A slow sync that takes more than 5 min (downloads/scan can) leaves `lastSlow` already older than 5 min when it finishes, so the next window activation starts another slow sync immediately. A slow that started 6 min ago and finished 1 min ago has the same problem. The throttle works for a short slow sync; it is not a “last refresh” throttle.
4. **`needsStatus` and `Ranking.overdueDays` — the pure function matches the spec.** `Ranking.overdueDays` is 14.0; `needsStatus` is true for ungraded due-tomorrow, due −13, due −14, false at −15/no cutoff, false when graded, true for `.distantFuture`; the P6 test covers those (`SelfCheck`). The P6 test **does not cover** the spec's “due 15 days ago, cutoff 3 days ahead → true” case, and `Moodle.sync` passes the **raw `cutoffdate`**, not the previous effective `cutoff`/extension (`Moodle.swift:217-219`). A late extension whose due date is more than 14 days old and whose raw cutoff is past can therefore be skipped, so its status/extension is never learned; a previous effective cutoff in `before` would avoid that.

## Findings

1. **High (conditional) — a failed/partial fast assignments call removes all deadlines until the slow tier.** `Moodle.swift:109-126` (assignments always from `fast`, never carried) + `Store.swift:155-183`. `mod_assign_get_assignments` is a soft call; one failure (network, token hiccup, course part skipped) gives a warning, `fast.subjects` have empty `assignments`, and the merge keeps that emptiness. The board loses every assignment card — while its marks stay — until the next slow sync (up to 60 min) or ⌘R. Fix: carry previous assignments for IDs the fast sync did not return (deleted ones may linger ≤60 min, like the deleted-forum note), or keep the previous assignments whenever the assignments call warned/failed; use a source-success flag.
2. **Medium — messages, notifications and calendar events are not carried over.** `Moodle.merge` carries announcements only when `source == .moodle` and events only when `resolvedVia == .coursePage` (`:119-124`). A fast fetch of messages/notifications is capped and can fail; old `.message`/`.notification` announcements disappear from the board (and a message can be the only place a deadline was stated), and a calendar/action failure drops previous teacher events. The General special-case (`:121-125`) carries only course-page pages, so a General made of messages/notifications/events vanishes if the fast sync has no General subject. Fix as in finding 1: carry previous non-coursePage events/messages not present in the fast result (stale ≤60 is already accepted for deleted forum posts).
3. **Medium — the 5-minute cameForward throttle uses the slow sync's start, not its completion.** `Store.swift:144-147` + `:184`. A slow sync longer than 5 min (or one started >5 min before an activation) is followed by another slow sync immediately; the comment says the throttle exists to avoid ~90 calls per app switch. Store a `lastSlowFinished` (or `lastCameForward`) timestamp and compare against that, or set `lastSlow` after the scan.
4. **Medium/Low — `needsStatus` uses the raw cutoff and can miss a late extension.** `Moodle.swift:217-219`: `cutoff: Self.date(a.cutoffdate)`, while `before[a.id]?.cutoff` (effective, extension-applied) is available. If the previous extension sets a future cutoff but the raw cutoff is past, an assignment due >14 days ago is skipped, so the status call that would return the extension never runs. Use the previous effective cutoff (or `max(raw, previous cutoff)`); add the spec's cutoff-future test and an extension case.
5. **Low — fast `summarize()` prunes paid titles against lossy subjects.** `Store.swift:179-183` calls `summarize()` on the fast result; `summarize` prunes `titles` to the fast subjects, so a title for a message/notification dropped by the merge is deleted and re-bought at the next slow sync. Keep the previous titles while a fast merge is lossy, or don't prune on fast.
6. **Low — deleted news/forum posts linger until the slow tier.** The merge carries every old `.moodle` announcement not in the fast result, including deleted news; the comment accepts this (≤60 min), but it also means a deleted announcement's date can stay on the board. Acceptable per spec, but note the asymmetry with messages (which are dropped immediately).
7. **Low — new course materials and course-page dates are absent until the first slow sync.** A newly discovered course in a fast sync has empty `materials` and no course-page events (fast `courseData` skips contents); the user waits up to 60 min for files and course-page dates. That is what O2 says (files slow), but a new course might warrant a one-off slow sync; note only.
8. **Test gaps.** The P6 tests are happy-path only: Tier, a few `needsStatus` cases (no cutoff-future/extension), a merge where fast has assignments, and General pages. There is no test for a failed fast assignments/messages/calendar call (findings 1/2), no test that a fast sync never calls `pruneBoardMarks` (finding 2 / focus), no 5-minute throttle test, and no `--moodle-check` fast/slow calls line (P6 check (d), target fast < 40).
9. **Verification:** P6 tests are committed and green in the 02:00 binary; the live fast/slow call counts and window-forward runs were not measured.
