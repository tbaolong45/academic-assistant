# B7 — bounded parallelism, PDF cache and the calls counter

Reviewer: DeepSeek #2 (read-only). Date: 2026-11-03.
Spec: `deadline-priority.md` §5.4 (bounded parallel calls), §5.3 (PDF text cache), B7 checks.
Snapshot: commit `40f62b7` (01:34); release binary 01:33; `SelfCheck.swift` 01:33. The binary was built before the B7 self-check tests were final (`b7:` checks exist in the source at `SelfCheck.swift:1140-1175` but are not in the run below); working tree clean.
Verification: `--self-check` on the 01:33 binary → **All checks passed**, but it contains **no `b7:` lines**; I did not run `--moodle-check` (no key) or measure calls/time.

## Focus answers

1. **Data races in the parallel paths — none found.** `Store` is `@MainActor`: `known`, `titles`, `summaryDone`, `classifierNote`, `summaryNote` are only touched in `learned`/`titled` and in the owning task on the main actor (`Store.swift:225-236`), while the `boundedMap` children only compute the answer and `await self?.learned/titled`; `Moodle`'s `courseData` keeps warnings in a local array and returns them with the `CourseData`, `CallCounter` uses `Mutex` (`Moodle.swift:36-41`), and `PDFCache` uses `Mutex` too. `boundedMap` writes its `out` array only in the parent task. Two remaining concurrency nits are below (cancellation, double PDF parse).
2. **Cancellation on first error — correct in `boundedMap`, weakened in Moodle.** `withThrowingTaskGroup` cancels the running children when a child throws, and classify/summarize keep every answer they already stored via `learned`/`titled` (`Store.swift:205-220`, `:257-275`). But Moodle's `soft` catches **everything except `invalidToken`**, including `CancellationError`, as a warning (`Moodle.swift:95-99`), and `courseData` has no `Task.checkCancellation()` between grades, contents and forums, so a group-cancelled course keeps issuing calls until it finishes. The submission-status closure also catches every error, so one failing assignment does not cancel the other status calls. On a fatal `invalidToken` the completed course data is discarded with the thrown `sync`, so Moodle answers are not “kept/cached” as the spec sentence implies.
3. **Warnings order — deterministic, untested.** `courseData` returns its local warnings; `boundedMap` returns results in input order; the `shown`/members loop appends `data.warnings` in the same course order as the old serial loop (`Moodle.swift:196-210`), and `statusError` is the first error in `assignIDs` order. No test compares the warning array against the serial order.
4. **PDF cache can serve stale dates — yes, through two paths.** The cache key includes Moodle's `size` and `modified`, but the download check `isSaved` compares **only size** (`Materials.swift:20-23`): a PDF updated on Moodle with a **new `timemodified` and the same byte size** is never re-downloaded, while `PDFCache.entry` sees the changed `modified`, misses the cache, and parses the **old local file** under the new key. Separately, the cache key has no local file identity/mtime (and `size == 0` means “any local file is saved”), so a locally replaced/zero-metadata file can hit the old entry. Finding 1/2.

## Findings

1. **High (conditional) — same-size PDF update never reaches the cache and returns the old dates.** `Materials.swift:20-23` (`isSaved` size only) + `:32-42` (`downloadMissing` skips) + `:123-145` (`PDFCache` re-reads on `modified` change). Scenario: `schedule.pdf` is updated so a date changes from “20 Oct” to “21 Oct” with the same byte count; Moodle reports a new `timemodified`; the app skips the download because the size matches; `PDFCache.entry` gets a key miss (new `modified`), calls `load` on the **old** file, and stores the old dates under the new key. Every later sync sees a hit and shows the stale date until the file size changes or the app restarts (even a restart re-reads the old file). Fix: make `isSaved`/`downloadMissing` compare `modified` (or persist the file's local mtime/size key) and invalidate the cache after a download; alternatively include the local file's mtime in `PDFCache.Key`.
2. **Medium — `PDFCache` key ignores the local file; unknown metadata is sticky.** `PDFCache.Key` has only `path/size/modified` and the dictionary is keyed by `path` (`Materials.swift:123-145`). A file replaced under the same Moodle size/modified, a file with `size == 0` (`isSaved` returns true for any existing file), or a local edit returns the old text/dates. `modified == 0` also makes the key constant (`posted` uses `.now` at first parse). Add the local file's modification date (or a content hash) to the key, and don't treat `size == 0` as “saved” when a re-download is needed.
3. **Medium — cancellation is swallowed by Moodle's `soft` and status closures.** `soft` (`Moodle.swift:95-99`) catches `CancellationError` as a normal warning; `courseData` (`:138-150`) never calls `Task.checkCancellation()` between its calls, so a cancelled group task keeps making grade/contents/forum calls; the status closure (`:175-183`) catches every error, so a bad token triggers all ~30 status calls instead of the first-error stop. The `boundedMap` group waits for these tasks, so cancellation is not prompt and a failing sync can still add load. Rethrow `CancellationError`, add `try Task.checkCancellation()` between the calls, and let the status calls cancel the group on a fatal error (keeping the per-assignment soft warnings).
4. **Low — completed Moodle course data is not kept on a fatal error.** `boundedMap` correctly throws on the first `invalidToken`, but the already returned `CourseData` is only in the local `fetched` array; `sync` throws before building subjects or saving `MoodleCache`, so those answers are lost. The spec's “answers already received are kept and cached” holds for classify/summarize (stored inside `f`) but not for Moodle. If auth failure partial data is not useful, say so; otherwise return a partial `MoodleSync`/save the completed courses behind a warning.
5. **Low — the PDF cache can parse the same PDF twice on first use.** `PDFCache.entry` checks the Mutex, releases it, calls `load`, then stores; two concurrent callers for the same key (e.g. `documentEvents` off-main and a preview's `mentions`) both miss and both parse. It is not a data race, but it violates §5.4's “parsed once per app run” and can be significant for large PDFs. Hold a per-key in-flight task or a lock across the load.
6. **Low — no B7 verification in the built binary.** `b7:` checks exist in `SelfCheck.swift:1140-1175` (PDFCache read-once/key change, boundedMap order/peak ≤4) but are absent from the 01:33 binary's output, and the live `--moodle-check` before/after counts (spec (c)) were not run. The B7 code compiles in the binary, but the cache/order behaviour is unproven until a rebuild and a `--moodle-check` from the app bundle.
7. **Low — warnings order / calls counter have no test.** The code is deterministic as described, but the only B7 checks are the cache and `boundedMap`; add a serial-vs-parallel warning-order test and assert the `calls` counter increments once per `call` (including failures).

## Checked and correct
- **`boundedMap`:** `withThrowingTaskGroup`, initial `min(max(limit,1), items.count)` children, one new child per completion, `(index, value)` results and `out` by index; outputs are in input order, the peak never exceeds the limit, empty input returns empty, and a thrown child cancels the group (`Model.swift:484-505`). The `Store` closures intentionally return `Void?`; the result is ignored.
- **Store:** classify limit 4 with `learned` per answer and a final `KindCache.save`; summarize limit 2 with `titled` and a save every 10; answers already received survive a later error; `classifyTask`/`summarizeTask` cancellation and generation guards remain; `summaryDone` is only touched on the main actor. No data race found.
- **Moodle:** per-course `courseData` (grades, contents, forums) at limit 4; submission status at limit 4 with `(status, ext, error)` results and the first error in `assignIDs` order; warnings stay in course order; `CallCounter` is `Mutex`-protected and `--moodle-check` prints calls and elapsed time. `courseData` returns warnings with the course, and the `shown`/members loop appends them in the old serial order.
- **PDFCache:** `Mutex<[String: (key, entry)]>`, `Key(path,size,modified)`, a hit only on exact key equality, `mentionedDates(..., strict: true)` built once and shared by `documentEvents` and `mentions`; per-run IP/year filters still apply after the cached `found` array; in-memory only, as specified. The unit test (source) covers read-once and re-read after `modified`; it does not cover the download/cache mismatch above.
- **Build:** self-check green on 01:33; B7's `b7:` checks are not in that binary (finding 6).
