## Focus answer — can stale data now hide a real change?

**Yes, for some edits/replacements; the calendar move is mostly safe.**

- **Edited post — stale when the title changes.** `Announcement.key` is `"title|creationDate"` (`Model.swift:213`). A teacher who edits an announcement's **title** changes the key; the fast result has the new post, but the previous post's key is not in `posts`, so `Moodle.merge` keeps the old announcement and every old event whose `announcement` is that key (`Moodle.swift:118-125`). The board can show the old deadline alongside the new one (or, inside one cluster, the new one may win; the old one is still there). This directly contradicts the merge comment “an edited post's new dates replace its old ones” — that only holds for body edits and unchanged titles. A body-only edit (same key) is replaced correctly.
- **Deleted assignment — stale by design.** A previous assignment whose ID is absent from the fast result is carried (`:117`, `:128`), so a genuinely deleted assignment lingers up to 60 min; the spec accepts this. **Replaced assignment:** if Moodle deletes and recreates it with a **new ID and the same title**, the old one is dropped (the title set matches) and the new one wins; if the replacement has a **new title**, the old assignment is carried too, so a stale old due/status remains on the board. A same-ID replacement (renamed/due changed) is replaced correctly. A `moodleID == nil` old-cache assignment is matched by title only.
- **Moved calendar event — normally safe.** `eventKey` prefers the stable `ref` (`:119`), so a moved Moodle calendar event keeps its id, the old previous event is found in the fast event set and not carried; an edited title/date with the same ref is also replaced. It goes stale only when the old event has **no `ref`** (pre-B2 cache; rare after the first slow sync) or its `ref` changes, or when the event is a **course-page** event (always kept until the slow tier, as intended). A deleted/replaced calendar event with a different ref also lingers up to 60 min.

## Findings

1. **Medium — an edited post title leaves the old announcement and its dates on the board.** `Announcement.key` includes the title (`Model.swift:213`), while `Moodle.merge` treats any missing key as “the post was deleted” (`Moodle.swift:118-125`). A title edit therefore carries the old post and all events that reference its old key; the new post/event is added too. The result is a stale deadline (possibly selected by Do next) until the next slow sync, or until the next fast title change. Fix: give `Announcement` a stable source id (discussion id/message id) or match posts by `(source, from, creation date)` ignoring the title, so a title edit is recognized as the same post; only carry when the post is genuinely absent. A test should edit the title and assert one post/one event.
2. **Medium/Low — a replaced assignment with a different title is carried as stale.** `Moodle.swift:117`/`:128` matches previous assignments by `moodleID`, else by title. Same-title replacements are handled, but a new-ID/new-title replacement keeps the old assignment (and its old due/status) alongside the new one until slow. This is the delete-linger trade for a normal delete, but it is not a normal delete for a replacement; consider a source-success flag (drop old assignments when a complete fast assignments call succeeded, carry only when it failed/warned), which would also make the deleted case precise.
3. **Low — a moved calendar event with a nil or changed `ref` is kept stale.** `eventKey` falls back to `date|title` (`:119`); a pre-B2 event has no ref, and a moved event changes the fallback key, so the old event remains. After the first slow sync every current event has a ref, so this is mostly a legacy-cache/edge case. Matching by title plus a stable source when the ref is absent would close it.
4. **Low — a new late extension still cannot be discovered if there is no previous effective cutoff.** F1k correctly uses `max(raw cutoff, previous effective cutoff)` (`Moodle.swift:227`), which fixes the known-extension case. But an extension granted to an assignment that is already more than 14 days overdue with no cutoff and no previous extension is still skipped by `needsStatus`, because the only call that would return `extensionduedate` is the one being skipped. The P6 rule intentionally accepts the 14-day limit; note the residual.
5. **Low — the throttle is now correct but untested.** `lastSlowFinished` is set after `scanDocuments` when `scanned` (`Store.swift:190`), and `cameForward` compares to it (`:146`); a slow sync that started 10 min ago and finished 1 min ago no longer triggers another. There is no test for this private path; the F1k test list only checks the merge and `needsStatus`.
6. **Low — deleted subjects/courses linger whole.** `subjects.append(p)` for every previous subject absent from the fast result (`Moodle.swift:112-113`) keeps a removed course (and its assessments/materials) up to 60 min. This follows the “deleted lingers” trade and fixes the General-only case, but it is broader than assignments/posts; accepted by the spec, worth stating.
7. **Test gaps:** no edited-title post, no deleted/replaced assignment, no moved-calendar ref/nil case, no `lastSlowFinished` throttle test, and no test that a missing course only lingers. The added tests cover the intended carry-over: 3 assignments kept when fast returns none, partial fast keeps the missing one, an updated assignment wins, a message/teacher event is kept, a General of messages survives, and the effective-cutoff `needsStatus`.

## Checked and correct
- **Assignments carry:** missing IDs are kept; a same-ID updated assignment wins; same-title replacement drops the old; a nil-ID previous assignment is matched by title; the result is sorted by due. Tests: all 3 kept with no fast assignments; `["A2","A3","A1"]` with the updated A1 due.
- **Messages/notifications/calendar:** announcements and events from every source are carried when missing (`:118-125`), not just `.moodle`/course-page; a `.message` and a teacher event are kept; a General made only of messages survives because previous subjects absent from fast are appended.
- **Moved calendar event:** a stable `ref` means the old event is not carried; a title/date change with the same ref is replaced; the exam test and the event ordering still pass.
- **Throttle:** `lastSlowFinished` is set only when the scan succeeded, after downloads and the PDF scan, and is not set on the failure branch; `cameForward` uses it and still requires `!syncing`; a fast sync does not update it, so a window-forward after 5 minutes of no slow still runs slow.
- **`needsStatus`:** cutoff is now `max(raw, previous effective)`; the 20-day-overdue + future effective-cutoff test returns true; graded/future/no-due cases remain as P6.
- **P6 test:** updated to expect `["Old","New task"]` for the carry-over; the earlier stale failure is gone.
