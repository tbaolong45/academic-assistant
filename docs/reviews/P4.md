## Answers to the two focus questions

**(1) Can a real per-message failure go uncounted, or a mail be skipped forever?**
Yes, in one conditional path. `SchoolMail.download` (`SchoolMail.swift:43-57`) catches `MailError.closed` and `break`s **before** counting a failure (`:49-50`). `.closed` means either "the connection is already dead, this UID was never attempted" (from `command`'s `dead` guard) **or** "the socket closed while this UID's FETCH was in flight" (from `receive`/`deadline`). The second is a real per-message transport failure and is not counted. If one UID reliably closes the socket (a message-specific server/parse problem), every sync restarts at that UID, breaks there, and counts nothing — so that UID is retried forever and **every later UID in that sync is never attempted**, i.e. newer mail can be starved indefinitely. The F1 test codifies the uncounted behaviour (`SelfCheck.swift:569-575`). Fix: distinguish "not attempted because dead" from "attempted but EOF" (e.g. throw a `connectionLost` from `receive`), count the latter once; after 3 the UID is skipped by `toFetch` and the rest proceeds (or reconnect and continue).
Two other skips are by design, not bugs: a `nil` from `message` (unparseable Date, or a reply without a literal) goes into `seen` forever (check d), and a UID with 3 failures is skipped until it leaves the 60-day search window (check b). The failure/seen counts are not shown in the UI, so those mails disappear silently (only the "skipped (unreadable date)" count is surfaced for `seen`).

**(2) Can the user's 50 cached mails be lost in the migration?**
Not for a valid old file. `MailStore.init(from:)` (`SchoolMail.swift:253-260`) decodes the old plain array first and maps it to `messages`, with empty `seen`/`failures`; the app's `load` therefore keeps all 50 (`MailCache.load` `:264`), `Store.init` merges `mail.messages` (`Store.swift:45`), and `addSchoolMail` starts from `start = mail` (`:204`) so `prune`/the per-message saves/the final save all carry them into the new keyed format. `writeOwnerOnly` writes before throwing, and `.atomic` keeps the old file if a write fails. The only losses are the pre-existing retention rule (`prune(since:)` drops messages older than 60 days on the next sync), a malformed old array (the whole `[Message]` decode fails, `load` returns an empty store, and the next sync overwrites the file — same as the old `try?` path), and the test gap noted in finding 4 (no round-trip check).

## Findings

1. **Medium (conditional) — a `.closed` during a message is uncounted and can starve later mail.** `SchoolMail.swift:49-50` (and the dead guard in `command` `:344-345`). Scenario as above; the F1 `dead` flag makes `.closed` a session-level signal, so `download` cannot tell "never attempted" from "attempt failed with EOF". The P4 unit check (c) uses an injected `.timeout`, which does not set `dead`, so it verifies "4 and 5 are still tried" only in isolation; after a **real** timeout the next UID throws `.closed` and the run stops (F1's intended behaviour), so the check's wording overstates the integration. Fix: a distinct error for an in-flight connection loss, count it for that UID, then stop.

2. **Low — `message` returning nil marks the mail seen forever, even when the cause is not the Date.** `SchoolMail.swift:366-368` returns nil both for `parse`'s missing Date and for a reply without a literal; `download` puts it in `seen` (`:47`). A transient truncated/odd reply therefore loses the mail permanently (check d describes the Date case). Acceptable for now; a separate "fetch failed" signal would avoid it.

3. **Low — failures never decay.** `toFetch` skips a UID from the 3rd failure on (`:37-39`) and `failures` is only cleared by a success or by `prune` when the UID leaves the search. A mail that timed out three times on a bad network is skipped for up to 60 days, with no UI entry (only `seen` is counted in the note). This is what check (b) specifies; noting it so the behaviour is deliberate.

4. **Low (test/migration coverage) — no new-format round-trip check.** `SelfCheck.swift:539-545` checks old-array decoding and `toFetch`; nothing encodes a `MailStore` and decodes it back, so a future change to `MailStore` or its `CodingKeys` could drop the cache silently (the old file is replaced after the first save). I verified the pattern independently with a scratch Swift program that copies `MailStore`'s structure and custom `init(from:)`: a keyed value round-trips, an old array decodes, and decoding a keyed value after the failed `[Message]` attempt works (2026-11-02). Add a two-line encode/decode check.

5. **Low (test fidelity) — check (c) does not simulate the dead connection.** `SelfCheck.swift:556-562` throws `.timeout` from the injected closure without `IMAPConnection` marking `dead`; in production that makes the next `message` throw `.closed` and the loop stop. The pure `download` contract ("a failing fetch doesn't stop the run") is tested, but the integration ("4 and 5 are still tried" after a real timeout) is not. Either add a second fixture that throws `.timeout` then `.closed`, or reword the check.

6. **Nit — the Store's mail note duplicates `MailStore.note`.** `Store.swift:220` builds `"… school emails · N skipped (unreadable date)"` by hand while `MailStore.note` (`SchoolMail.swift:243`) has the same text and is the one check (e) tests; use `mail.note` so they cannot diverge.
