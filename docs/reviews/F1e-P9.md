## Focus answers

1. **Can a merge still hide a real deadline? Yes, three residual ways.**
   - **Calendar/Outlook different-ref events can still merge through a news bridge** (finding 1): the F1e #1 guard is pairwise, and the cluster-root guard only tracks `ref → date`, not calendar refs.
   - **Numeric, dotted and relative dates are not in `namedDays`** (finding 2): the day rule only sees weekdays plus `dayMonth`/`monthDay`, so "Quiz on 23/10" / "Quiz on 25/10" (or today/tomorrow) remain two different items with an empty day set and merge.
   - **Two generic same-title events with no named date** still take the exact-title fast path within 3 days (finding 3); the day guard is skipped whenever either day set is empty (finding 4).
2. **Does P9 ever skip a title that is actually shown on the board? No, not for a visible card.** `Summarizer.targets` (`Summarizer.swift:148-159`) only adds `d.alsoIn` member ids of a visible Moodle-activity cluster and every id of a hidden cluster; the **winner** of a visible cluster is never skipped, and an activity winner is not a `CourseEvent` at all. Members of an activity cluster are not a card (the card shows the activity title), so no visible AI title is lost. The reverse is the issue: the target filter does **not** require the event to be on the board, so it still pays for titles nobody sees (finding 6), and board items outside the 7/120-day window are shown but never titled (finding 7, pre-existing).

## Findings

1. **Medium — two calendar events with different refs can still merge via a news bridge.** `Model.swift:590-624`. F1e #1 rejects an A/C pair (both `moodleCalendar`, refs 41/42, neither moved), but the union-find can join A–B (B is a news mention) and B–C because B is not a calendar. The root-level guard (`:615-618`) checks activity and `refDates` only, not “this cluster already has a calendar event with another ref”. Scenario: a teacher's calendar has “Seminar” on 20 Oct (ref 41) and 22 Oct (ref 42), and a news post says “Seminar” on 21 Oct; all three end up in one cluster and one event is lost. Same for two Outlook UIDs. Fix: keep a per-root set of `(origin, ref)` for `moodleCalendar`/`outlookCalendar` and refuse a union that would put two different refs of one origin in one cluster (a stated move can still be allowed if desired). No test covers the bridge; the F1e #3 test only bridges a **PDF** ref.

2. **Medium — `namedDays` ignores numeric and dotted dates and relative day words.** `Moodle.swift:484-500` collects weekdays and `dayMonth`/`monthDay` (month names) only; `mainPoint` strips `23/10` from the title, the day set is empty, and two events “Quiz 3 on 23/10” and “Quiz 3 on 25/10” have the same words/numbers and a 2-day gap, so they merge. “Quiz today” / “Quiz tomorrow” do the same (`clusterSkip` removes today/tomorrow from the words, `namedDays` doesn't add them). Explicit dates are what F1e #2 promised; numeric dates are the most common form in Moodle posts. Add the `numeric` regex (and the dotted form / today/tomorrow) to `namedDays`, or leave the day set empty only when the title truly has no day.

3. **Low–Medium — two generic same-title events with no named day still merge.** `Model.swift:608` exact-title fast path: “Class cancelled” on Monday and “Class cancelled” on Tuesday (no day word in title/detail) have empty day sets, the same words and a 1-day gap → one card. The same applies to “Make-up class”, “Final submission”, two PDF rows from different files, etc. The user's rule (“a vanished card is worse than a duplicate”) suggests a same-source/same-announcement guard when both titles are generic and neither carries a day/number/move. The current tests only cover titles that name a weekday.

4. **Low — the day guard is skipped when either side has no day.** `Model.swift:602`: “No classes” (empty) vs “No classes on Tuesday” (one day) falls through to `sameItem`/words and merges, though the first may cover a different scope. Requiring a day on both is safe for the “one side names a day” case; consider treating an empty day set as “unknown” and requiring another identity (number/ref) before merging two day-named items.

5. **Low — the calendar guard needs both refs.** `Model.swift:598-599` only rejects when `let ra`, `let rb` are present; a pre-B2 cache (nil refs) or one old/new event pair can still merge two calendar events with the same title within 3 days until the next sync fills `ref`. Transient, but worth a comment.

6. **Low–Medium — P9 still pays for titles that are not on the board.** `Summarizer.targets` (`:157-158`) filters only `window`, `kind.isDated`, `titles == nil` and the hidden/activity set. It does not apply `deadlines()`'s `hasContent(e.title)` or the `sameItem` event-vs-assessment dedupe (`Model.swift` events filter), so a bare “Dec 8 — -” line or an event hidden behind a same-named assessment gets a Jev/DeepSeek title although no card ever shows it. That contradicts the doc comment “with a card someone can see” and P9's cost purpose. Add `hasContent` and a board-membership check (event id in some visible cluster or its own cluster) before targeting.

7. **Low — the title window is narrower than the board.** `Store.swift:213` targets −7…+120 days; the board holds all dates (B1). A card more than 120 days out (or a past one beyond 7 days) is visible in the week board but never gets an AI title. Pre-existing, not introduced by P9, but the focus question “title actually shown” has this yes.

8. **Test gaps.** No F1e test for the calendar/Outlook news bridge, numeric/dotted/today-tomorrow days, generic no-day same-title, or one-side-empty days; no P9 test for a non-board event (`hasContent`/sameItem), a visible winner with a title, the 120-day window, or a cluster split after a skip. The current tests do cover the direct pair guards, the weekday cases, the supersede order, the PDF-ref bridge, and the open/submitted P9 fixture.

## Checked and correct
- **F1e #1 direct pairs:** two Moodle calendar events with different ids and two Outlook events with different UIDs stay two cards; the pair test passes. The guard is skipped when a stated move (`moved == true`) is present, as specified.
- **F1e #2 weekdays:** “Class moved to Tuesday”/“…Thursday” and “No classes on Monday”/“…Tuesday” stay two cards; the newer-move/older-not supersede (“Quiz 3 on Tuesday” → “moved to Thursday”) merges and takes Thursday, and the reversed post order stays two; tests pass. `clusterSkip` still strips weekdays from the word overlap, so the new day rule is what separates these.
- **F1e #3 ref bridge:** the per-root `refDates` map plus the union check now blocks a news mention from chaining one PDF ref at two dates; the PDF-row and bridge tests pass.
- **P9 target decision:** `targets` recomputes from the current `board` (`items`) every run; activity-cluster members and hidden clusters are skipped; a submitted assignment (activity leaves the board) makes the post targetable; the open/submitted fixture returns 0/1. Prune still uses all subjects' events, so hidden members' paid titles are kept; the cluster-split path is naturally retried on the next run.
- **P9 does not skip a visible winner:** the hidden set contains `d.id` only for hidden clusters and `alsoIn` ids for hidden/activity clusters; a visible cluster's winner is never in it. An activity winner is a `Deadline`, not a `CourseEvent`, so it has no summarizer target of its own.
- **Build:** the 00:54 release binary (which includes the working F1f/B6 changes) passes all checks; the P9/F1e checks are green.
